# Архитектура MVP

Решение архитектора от 2026-11-21 по [requirements.md](requirements.md). Код прежней реализации не читался. Статус каждого пункта, требующего согласия владельца, — в разделе «Согласования».

## Слои и каталоги

| Каталог | Что внутри |
|---|---|
| `core/` | Без WinAPI-хуков, тестируется вне 1С: `color` (движок цвета), `json` (строгий парсер, ≤ 256 КБ), `png` (свой inflate, 8-bit RGBA/RGB), `hash` (FNV-1a/64 по пикселям без stride), `dup` (детектор дублей), `glyph_layout` |
| `patch/` | Разбор PE, патчи EAT и IAT (включая delay-load), стабы, журнал отката |
| `theme/` | DLL темы |
| `probe/` | Диагностическая DLL, только чтение |
| `loader/` | Нативный загрузчик |
| `tests/` | Юнит-тесты и `testlib.dll` для патч-движка |
| `themes/default/` | `palette.json`, `icons.json`, `icons/*.png` |

Сборка: `build.cmd x86|x64 [debug]` — vswhere → vcvarsall → `cl`/`link`, без CMake; `/MT /EHs-c- /GR- /O1 /GS /guard:cf /DYNAMICBASE`; артефакты в `out/<arch>/`; шаг проверки `dumpbin /dependents` — только `kernel32`, `user32`, `gdi32`.

## Жизненный цикл DLL

- `DllMain`: только `HINSTANCE`, `DisableThreadLibraryCalls`, критическая секция. Без файлов и патчей под loader lock.
- Работа — в экспортах, которые загрузчик вызывает отдельным удалённым потоком: `DtStart` (читает JSON/PNG, строит таблицы, ставит патчи, возвращает код) и `DtStop`. Своих фоновых потоков нет.
- `DLL_PROCESS_DETACH` без `DtStop` и с `reserved == NULL` — аварийный откат журнала; при выходе процесса ничего не делать.
- Защита от повторной загрузки — именованный объект `Local\…-<pid>`.
- `cairo.dll` статически не импортируется: адреса через `GetModuleHandleW` + исходный EAT. Нет экспорта — хук не ставится, причина в лог.

## Движок патчей

- Для каждого перехваченного экспорта — стаб `jmp [slot]` в странице `VirtualAlloc` (x64 — в окне `[base, base + 4 ГБ)` поставщика). В EAT пишется RVA стаба, не попадающий в каталог экспорта; форвардеры не патчатся.
- IAT и delay-load IAT всех модулей, кроме своего: слот меняется, только если в нём исходный адрес экспорта.
- Журнал пишется до записи в слот (адрес, исходное значение, ширина: EAT — 4 байта, IAT — указатель). Журнал полон — патч не ставится.
- `DtStop`: флаг `active = false` → откат IAT → откат EAT → второй обход IAT (адреса стаба/хука, полученные поздними модулями) → стабы атомарно переводятся на исходные функции → ожидание нуля счётчиков входов + пауза → освобождение защиты от повтора.
- Страница стабов не освобождается (≤ 3 страниц за цикл): она обезвреживает адреса, сохранённые через `GetProcAddress` вне IAT.
- Счётчики входов — по слотам с ключом от tid, каждый в своей кэш-линии; глобальной блокировки нет.

## Движок цвета

- Две карты по **исходному** цвету: `map_fill` применяется в `set_source_rgb/rgba`, `map_text` — в `show_glyphs`. Исходный цвет хранится в слоте потока по `cairo_t*`, чтобы светлый текст не затемнялся как «бледный фон».
- Порядок: квантование до 8 бит → контекст (`editor`, `panel`, `popup`, `help`, `dialog`; у GDI — `gdi`) → точная таблица контекста → общая таблица → ближний цвет с допуском → правило для неизвестных цветов.
- Правило для неизвестных цветов зависит от роли: заливка — бледное темнеет с сохранением оттенка; текст — светлеет до `min_contrast` к фону контекста с сохранением оттенка.
- Целевая схема владельца — неподвижные точки «цель → цель»: ручные настройки пользователя не перекрашиваются второй раз.
- Фаза текста: `cairo_save` → `set_source_rgba(текст)` → исходная функция → `cairo_restore` — цвет до отрисовки, пиксели не пишутся.
- Мемо-кэш с открытой адресацией, запись — атомарное 64-битное значение; немаппленный цвет проходит без изменений, альфа не меняется.

## Детектор дублей

- Сигнатура прогона: хеш индексов глифов + число + цвет + `cairo_get_target`. Кольцо последних прогонов в фиксированной таблице; коллизия — без пропуска.
- Пропуск второго прохода: та же сигнатура и поверхность, |dx|, |dy| ≤ порога из JSON.
- Включается только после живой самопроверки раскладки глифа; провал — пропуск выключен на сессию, причина в лог. x64: 24 байта, `x` по 8, `y` по 16 (`static_assert`); x86 — только самопроверка.

## Значки

- В `cairo_pattern_create_for_surface`: поверхность IMAGE, ARGB32, размер из таблицы → хеш данных (только чтение) → совпадение → исходная функция с нашей поверхностью.
- Наша поверхность создаётся при старте через `cairo_image_surface_create`, память принадлежит cairo — паттерны, которые 1С держит после выгрузки, не висят.

## Форматы

```json
{"schema":1,"name":"…","tolerance":6,
 "contexts":{"editor":{"bg":"#202028","text":"#F8F8E8"},"panel":{},"popup":{},"help":{},"dialog":{}},
 "map_fill":[{"from":"#RRGGBB","to":"#RRGGBB","ctx":"editor|*"}],
 "map_text":[{"from":"#RRGGBB","to":"#RRGGBB","ctx":"editor|*"}],
 "syscolors":{"<idx>":"#…"},
 "fallback":{"pale_min":0.55,"bg_l":[0.08,0.2],"min_contrast":4.5},
 "dup":{"max_dx":3,"max_dy":3,"ring":256}}
```

`icons.json`: `{"schema":1,"hash":"fnv1a64-argb32-v1","icons":[{"hash":"…","w":16,"h":16,"png":"icons/save-dark.png"}]}`.

Ошибка разбора: `DtStart` возвращает код, ничего не патчится, загрузчик выгружает DLL, процесс жив.

## Загрузчик

Два `.exe` из одного исходника — по одному на битность.

Команды: `load`, `unload`, `status`, `probe-load`, `probe-dump`, `probe-unload`; `--pid` допустим только со всеми проверками.

Проверки до открытия процесса на запись. Права на запись (`PROCESS_CREATE_THREAD`, `PROCESS_VM_OPERATION`, `PROCESS_VM_WRITE`) — только после всех проверок. До проверок 1, 2 и 4 процесс открывается только с `PROCESS_QUERY_LIMITED_INFORMATION | SYNCHRONIZE`; чтение памяти цели (снимок модулей Toolhelp, `PROCESS_VM_READ` для сверки заголовка модуля при выгрузке) — только после проверок образа, окна и битности.

1. Образ — ровно `1cv8.exe`.
2. Видимое окно верхнего уровня этого pid, в заголовке которого в любом месте есть подстрока «Конфигуратор» (решение владельца 2026-11-22).
3. Загрузчик сам наблюдает окно непрерывно ≥ 25 с и проверяет возраст процесса ≥ 25 с.
4. Битность цели, загрузчика и `Machine` DLL совпадают.
5. В процессе нет темы и probe любой битности.
6. DLL — только соседний файл с фиксированным именем, путь нормализован; параметра `--dll` нет.
7. Несколько подходящих целей без `--pid` — отказ.

После `OpenProcess` образ и время создания проверяются повторно. Модуль ищется снимком по полному пути, `DtStart` вызывается по RVA из файла. Выгрузка — только своего модуля: `DtStop` (5 с) → `FreeLibrary` → проверка → перерисовка.

Уточнения реализации (M2):

- Окно — видимое, верхнего уровня, без владельца; правило заголовка — одна функция `classify_title` в `loader/loader.cpp`: подстрока «Конфигуратор» в любом месте заголовка (решение владельца 2026-11-22). Фактический формат 8.3.27 x64: «<активное окно> - Конфигуратор - <имя конфигурации>», без открытых окон, вероятно, «Конфигуратор - <имя конфигурации>»; часть до слова меняется при переключении окон внутри 1С. Поэтому наблюдение 25 с держится за то же окно (тот же HWND и pid, видимое, без владельца) и наличие слова на каждом опросе, а не за неизменность заголовка. `status` печатает только «есть / нет», сам заголовок — никогда.
- Проверка 5: именованный объект `Local\cfgdark-<pid>` (общий для темы и probe, поэтому они не активны вместе) и снимок модулей Toolhelp по именам `cfgdark_{theme,probe}_{x86,x64}.dll`. Снимок только читает память цели; на запись процесс открывается после всех проверок.
- DLL: каталог загрузчика и путь DLL берутся после разрешения ссылок (`GetFinalPathNameByHandleW`), только локальный `X:\…` короче `MAX_PATH`; файл держится открытым без общего доступа на запись до конца операции.
- `DtStart`: 0 — успех, 1 — тема или probe уже активны (код 10), прочее — код 12; при ненулевом коде DLL выгружается. `DtStart` не завершился за 10 с — код 12, модуль остаётся.
- Выгрузка: те же проверки цели, без 25-секундного наблюдения. Заголовок модуля в памяти (`Machine`, `TimeDateStamp`, `SizeOfImage`) сверяется с файлом; несовпадение или модуль с нашим именем из другого каталога — код 16. `DtStop` вернул не 0 — код 14, `FreeLibrary` не вызывается.
- Блокировка операции: `load`, `unload`, `probe-load`, `probe-unload` (с M3b и `probe-dump`) над одним pid сериализуются именованным mutex `Local\cfgdark-op-<pid>` (pid десятичный). Создаёт и держит его только загрузчик, DLL его не открывает. Захват — `CreateMutexW` и ожидание 0 мс сразу после проверки битности, до чтения DLL, объекта активности и снимка модулей; держится всю команду вместе с 25 с наблюдения и освобождается (`ReleaseMutex`, `CloseHandle`) на любом исходе перед закрытием описателя процесса. Решение — по результату захвата, а не по `ERROR_ALREADY_EXISTS`. Занято, нет доступа к имени или имя занято объектом другого типа — сразу код 17, без ожидания; прочие ошибки — код 11. `WAIT_ABANDONED` (прежний загрузчик прерван) — предупреждение, операция продолжается с полной перепроверкой, код выхода не меняется. Загрузчик другой битности получает код 6 раньше и блокировку не берёт. `status` блокировку не открывает и не ждёт; снимок модулей снимает только у цели своей битности, иначе печатает «модули: не проверялись» с причиной. Ограничения: блокировка сериализует загрузчики, но не удалённые потоки, пережившие свой таймаут (M4); имена `Local\` предполагают одну сессию у загрузчика и `1cv8.exe`; процесс того же пользователя, занявший имя заранее, даёт только отказ 17.
- Перерисовка на M2 — R1 видимым окнам цели и их дочерним.
- `probe-dump` до M3b отвечает «не реализовано» с кодом 2.

| Код | Значение |
|---|---|
| 0 | успех |
| 2 | использование |
| 3 | нет цели |
| 4 | цель неоднозначна |
| 5 | окно не простояло 25 с |
| 6 | несовпадение битности |
| 7 | DLL отсутствует, неверный путь или машина |
| 10 | уже загружено |
| 11 | ошибка WinAPI |
| 12 | `DtStart` вернул ошибку |
| 13 | не загружено |
| 14 | `DtStop` не завершился |
| 15 | модуль остался после `FreeLibrary` |
| 16 | выгрузка чужого модуля отклонена |
| 17 | над pid уже идёт операция другого загрузчика |

## Замер

- **С экрана (computer use, только основная сессия, без загрузки DLL):** непрозрачные фоны, рамки, заливки всех контекстов в светлой теме; визуальная приёмка вех. Снимки — только в scratchpad сессии, в git не попадают; в документацию — только числа. Проверка искажений (ночной режим, HDR, профиль) по известному `#FFFFFF`.
- **`GetSysColor`** — загрузчик читает сам вне процесса.
- **Probe** — три хука `cairo.dll`, только чтение, всегда вызывают исходную функцию:
  1. `cairo_pattern_create_for_surface` — хеши поверхностей 8…48 px, размер, формат, вызывающий модуль;
  2. `cairo_show_glyphs` — правдоподобие раскладки (0/8/16 и 0/4/12), исходный цвет текста и лексем, гистограмма dx/dy пар дублей с признаком «тот же поток / та же поверхность»;
  3. `cairo_set_source_rgba` — только вызовы с альфой < 1.

  Не пишет текст, индексы глифов, заголовки окон. Грузится только после подтверждения «окно открыто ≥ 25 с» и никогда вместе с темой.

## Исследования

**Двоение при первом рендере.** Гипотезы: H1 — двухпроходный текст запекается в кэш строк; H2 — пара приходит из разных потоков или на разные поверхности; H3 — двойная раскладка с очищающей заливкой мимо карты; H4 — подсветка поверх текста по умолчанию даёт ореол. Диагностика probe в светлой теме («открыть новый модуль» против «прокрутить открытый») и диагностический режим темы. Контроль: модуль, открытый под темой, после выгрузки не двоится.

**Признак готовности вместо паузы 25 с** (запрос владельца, 2026-11-22). Время построения стартовых кэшей 1С зависит от ПК, конфигурации и версии платформы, поэтому фиксированная пауза — запас, а не замер. Эталон — probe на M3b: момент, после которого перестают создаваться новые поверхности и паттерны. Кандидаты для загрузчика (снаружи, без чтения файлов ИБ): `WaitForInputIdle`, стабилизация набора окон процесса, стабилизация списка модулей. Выбирается признак, который надёжно наступает после эталона. До замера и решения владельца порог 25 с не меняется.

**Перерисовка без ресайза** — только окнам целевого pid, без широковещания, по одному механизму:

| | Механизм | Риск |
|---|---|---|
| R1 | `InvalidateRect` + `UpdateWindow` для окна и всех дочерних | низкий |
| R2 | `SetWindowPos(SWP_FRAMECHANGED…)` без смены геометрии | низкий |
| R3 | `WM_SIZE` с текущим размером | средний |
| R4 | `WM_SYSCOLORCHANGE` / `WM_THEMECHANGED` / `WM_SETTINGCHANGE` | высокий: 1С может перестроить кэши под темой |
| R5 | программный ресайз ±1 px с возвратом (запасной) | низкий, не для развёрнутого окна |

Критерии: без темы кадр не меняется; под темой охват по счётчикам; после выгрузки тот же триггер даёт исходный светлый кадр.

## Настройки конфигуратора

Путь A: тема перекрашивает при отрисовке, настройки 1С не читаются и не пишутся. Путь B (правка настроек) не проектируется. Гибрид — разовая запись в настройки только того, что безопасно и в светлой теме (шрифт, различимые оттенки совпавших категорий), — рассматривается только по решению владельца после замера хранилища.

Предел пути A: категории различаются только по исходному цвету; совпадения цветов 1С по умолчанию (подозрение: ключевые слова и операторы, комментарии и препроцессор, фоны поиска, подсказки и выделения) выясняет замер на профиле с настройками по умолчанию. Шрифт перекраской не задать.

## Риски

1. Гонка выгрузки: поток внутри исходной функции, вызванной из хука. Закрывается счётчиками входов и порядком `DtStop`; нарушение порядка роняет `1cv8.exe`.
2. Многопоточность cairo: без блокировок, атомарные 64-битные записи (на x86 — Interlocked), коллизии детектора — без пропуска.
3. CFG/ACG у `1cv8.exe`: при запрете динамического кода стабы не создать → на x64 только IAT; загрузчик диагностирует политику.
4. Версии 8.3.14–8.5.1: набор экспортов cairo и формат заголовка окна могут отличаться — отсутствующий хук пропускается с записью в лог.
5. Двоение первого рендера может оказаться кэшем, запечённым при открытии модуля; если причину нельзя убрать до отрисовки, фикс в рамках SKIP-ONLY невозможен — решение владельца после M6.
6. Значок: если 1С кэширует паттерн, после выгрузки «Сохранить» может остаться тёмным — проверка на M7.
7. Если замер покажет цвета или значки через `comctl32`, `uxtheme` или `windowscodecs` — новый модуль, решение владельца.
